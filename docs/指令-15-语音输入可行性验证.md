### 但日志质量有两个问题

实机跑出来的真实日志开头长这样：

```text
[warn] (electron) 'safeStorage.isEncryptionAvailable' is deprecated and will be removed...
[warn] (electron) 'safeStorage.encryptString' is deprecated and will be removed...
[info] [hermes-pet] 已从 Hermes 导入 DeepSeek 密钥（长度 35，base https://api.deepseek.com/v1）
[info] [hermes-pet] 自动导入密钥： 成功
[info] [hermes-pet] bridge listening on 127.0.0.1:50177
```

**问题一：Electron 自己的弃用警告被一起吃进日志了。** `console.warn` 被接管后，Chromium / Electron 内部打的警告也落到文件里，每次启动至少两条。日志是给人查问题用的，被这类噪音占开头，真正有用的信息就被推远了。

修法：接管时过滤掉 `(electron)` / `(node)` 前缀的内部警告，只让业务日志进文件。

```js
console.warn = (...args) => {
  const first = String(args[0] || '');
  if (first.startsWith('(electron)') || first.startsWith('(node)')) return;  // 框架噪音不进日志
  logger.warn(...args);
};
```

`console.log` / `console.error` 同样处理。

**问题二：密钥相关的信息进了日志文件。**

`已从 Hermes 导入 DeepSeek 密钥（长度 35，base https://...）` 这句虽然没打 key 本身，但把「有几个字符、走哪个 base」写进了明文日志。日志文件将来可能会被发出来排查问题。

改成只说结果，不说细节：

```diff
- console.log(`[hermes-pet] 已从 Hermes 导入 DeepSeek 密钥（长度 ${key.length}，base ${base}）`);
+ console.log('[hermes-pet] 已从 Hermes 导入密钥');
```

**通用原则**：日志里不要出现密钥、token、完整 URL 带 query 的、用户输入的消息内容。这轮顺手把现有几处扫一遍。

## 二、这一轮要回答的问题

路线图最后一项是「语音输入转写走本地 ASR（当前仅浏览器 SpeechRecognition 入口）」。

但在决定装什么之前，有件事没人验证过：**`webkitSpeechRecognition` 在 Electron 里到底是能用，还是只是个能 `start()` 的空壳。**

我实测过一半：

```text
typeof window.SpeechRecognition          "function"
typeof window.webkitSpeechRecognition    "function"
r.start() 后 5 秒内的事件                ["start"]   ← 没报错
麦克风设备（enumerateDevices）            4 个，USB 麦克风 + 英特尔阵列都在
```

`start` 能走通、麦克风也在，但**没有一个字被识别出来过**——因为我没法对着麦克风说话。所以现在处于最尴尬的状态：看着像能用，实际可能点了没反应。

`renderer/chat.js:393-425` 的错误处理写得很规矩（`onerror` 会提示「麦克风权限被拒绝」或「语音识别失败」），但它处理的是**已知的**失败——如果 Chromium 的语音服务在 Electron 里根本不存在，表现可能是 `start` 之后永远等不到 `onresult`、也不报错，用户点了就干等。

## 三、先做验证，别急着装东西

### 第一步：在打包版里点一次语音按钮，说一句话

要让**用户本人**做这一步（对着麦克风说中文），自动化测不了。但你可以先把验证环境做到最省事：

1. 在 `renderer/chat.js` 的 `setupVoice()` 里，把关键事件加进日志：

```js
recognition.onstart   → window.pet.log('info', '[asr] start')
recognition.onresult  → window.pet.log('info', '[asr] result', transcript)
recognition.onerror   → window.pet.log('warn', '[asr] error', event.error)
recognition.onend     → window.pet.log('info', '[asr] end')
recognition.onaudiostart  → window.pet.log('info', '[asr] audiostart')
recognition.onaudioend    → window.pet.log('info', '[asr] audioend')
recognition.onspeechend   → window.pet.log('info', '[asr] speechend')
```

`onaudiostart` / `onspeechend` 这两条特别关键：**如果麦克风真的采到声音了，它们会触发；如果语音服务不存在，这两个事件通常根本不来。**

2. 顺便加一个 5 秒超时兜底，让"点了没反应"这件事变得可见：

```js
let gotAnything = false;
recognition.onaudiostart = () => { gotAnything = true; ... };
recognition.onend = () => {
  if (!gotAnything) {
    $('input').placeholder = '语音服务没有响应：麦克风没采到声音，或系统没有可用的中文识别';
  }
  ...
};
```

3. 打一个包，让用户点一次，把日志发回来。

### 第二步：按日志判定走哪条路

| 日志表现 | 结论 | 下一步 |
|---|---|---|
| 出现 `[asr] audiostart` → `[asr] result 今天还剩什么活` | **浏览器识别是好的** | 不用装任何东西。这一项改成「补交互反馈」就收工：录音波形、按住说话、识别中状态 |
| 出现 `[asr] audiostart` 但永远没有 `result`，最后 `error: network` | Chromium 没带语音服务 | 走本地引擎，见第四节 |
| 完全没有 `[asr] audiostart` | 麦克风权限或设备问题 | 先查权限，别急着换引擎 |
| 点了按钮什么都没打出来 | 代码路径没走到 | 先查 `voice-btn` 的绑定 |

**在拿到这份日志之前，不要动手装任何引擎。** 装错了要卸载、要清模型文件，成本比多等一次验证高得多。

## 四、如果确实要上本地引擎：三条路的实际代价

拿到日志确认浏览器识别不可用之后，再按这张表选。**先给结论：我推荐 sherpa-onnx。**

| 方案 | 体积 | 中文效果 | 集成复杂度 | 备注 |
|---|---|---|---|---|
| **sherpa-onnx**（推荐） | 引擎 ~15MB + 中文流式模型 ~120MB | 好，支持流式（边说边出字） | 中：npm 有 `sherpa-onnx-node`，原生模块，要给 electron-rebuild 配 | 支持 VAD 内置，静音自动断句现成 |
| vosk | 引擎 ~10MB + 中文模型 ~42MB | 一般，安静环境可用 | 低：`vosk` npm 包，纯 Node 绑定 | 体积最小，但识别质量明显差一档，口音重的场景错得多 |
| whisper.cpp | 二进制 ~5MB + base 模型 ~140MB | 好，但非流式 | 高：要自己管二进制、音频重采样、分块 | 现在 Hermes 本机就装着 faster-whisper（base），理论上能复用，但要跨进程调，接口得自己搭 |

选 sherpa-onnx 的理由：流式输出对桌宠这个场景体验差别很大（说完才出字 vs 边说边出字），而且它自带 VAD，省掉自己写静音检测那一大块。

**但这轮不要动手实现。** 这轮的交付物是：第三节的日志 + 一份实测结论。装引擎是下一轮，而且要等用户看过体积之后点头。

## 五、验收

这轮只交付两件事，别多做。

1. **日志改动**：`console.*` 接管时过滤 `(electron)` / `(node)` 噪音；密钥相关日志改成只报结果；`chat.js` 的 `setupVoice` 里加 6 个事件日志 + 5 秒超时兜底
2. **一份实测结论**：打一个新包，用户点一次语音按钮说一句话，把 `%LOCALAPPDATA%\hermes\logs\pet-*.log` 里 `[asr]` 开头的所有行原样贴出来

### 汇报格式

```text
1. git log --oneline -2
2. 日志文件开头 6 行（证明噪音过滤生效，不应该再看到 (electron) deprecated）
3. 用户点按钮后日志里所有 [asr] 开头的行，一行不漏
4. 按第三节那张表，判定属于哪种情况
5. npm test / smoke
6. 如果走本地引擎，把第四节那张表按你的实际调研更新一遍（体积、npm 包名、license），然后停在这里等确认
```

第 3 条是这轮唯一真正重要的东西。**没有 `[asr]` 日志就等于没验。**

## 六、不许做的

1. **不要在这一轮装任何 ASR 引擎或下载模型**。`package.json` 这轮不加新依赖
2. **不要为了"验证方便"把 `voice-btn` 改成自动启动录音**。麦克风必须用户手点，这是隐私边界
