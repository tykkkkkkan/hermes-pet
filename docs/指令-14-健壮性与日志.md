### `ENOTFOUND` → `net.fetch` 这条查得很准

先加日志拿到 `cause: ENOTFOUND` 再动手，不是猜着换 API，这是正确的排查顺序。`ENOTFOUND` 说明 Node 的 undici 完全绕过了系统代理，域名解析根本没出去；换成 `net.fetch` 走 Chromium 网络栈继承代理设置，一次解决。这轮最值钱的就是这个动作。

## 二、现状：坏了以后没有任何线索

```text
console.* 调用        6 处（错误路径只有 1 处：模型请求）
日志落盘              没有
uncaughtException     没有
unhandledRejection    没有
render-process-gone   没有
```

打包版的 `console.log` 用户看不到（没有终端窗口）。所以现在的实际体验是：

- 主进程抛个没接住的异常 → 桌宠直接消失，用户不知道为什么
- 渲染进程崩了（显卡驱动、内存不足）→ 桌宠窗口变成空白，一直白着
- 桥接服务绑端口失败 → 插件调工具返回"桌宠没有运行"，但其实进程活着
- 状态文件写坏了 → 好感度、心情悄悄归零，用户以为是自己记错了

这四条都不会自己恢复，也不会留下任何记录。**这就是这一轮要补的。**

## 三、第一步：日志落盘

### 新增 `logger.js`

```js
const fs = require('fs');
const path = require('path');

module.exports = function createLogger({ logDir, maxDays = 7, now = () => new Date() }) {
  let stream = null;
  let currentDay = '';

  function dayKey(d) {
    return `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}-${String(d.getDate()).padStart(2, '0')}`;
  }

  function open() {
    const d = now();
    const key = dayKey(d);
    if (key === currentDay && stream) return;
    currentDay = key;
    try {
      fs.mkdirSync(logDir, { recursive: true });
      stream?.end();
      stream = fs.createWriteStream(path.join(logDir, `pet-${key}.log`), { flags: 'a' });
    } catch {
      stream = null;   // 日志写不了也不能把主流程拖死
    }
    prune(d);
  }

  function prune(d) {
    // 只留最近 maxDays 天，防止一天几百条把磁盘堆满
    try {
      const cutoff = d.getTime() - maxDays * 86400000;
      for (const name of fs.readdirSync(logDir)) {
        const m = name.match(/^pet-(\d{4})-(\d{2})-(\d{2})\.log$/);
        if (!m) continue;
        if (new Date(`${m[1]}-${m[2]}-${m[3]}`).getTime() < cutoff) {
          fs.unlinkSync(path.join(logDir, name));
        }
      }
    } catch {}
  }

  function write(level, args) {
    open();
    const text = args.map((a) => {
      if (a instanceof Error) return `${a.message}\n${a.stack || ''}`;
      if (typeof a === 'object') { try { return JSON.stringify(a); } catch { return String(a); } }
      return String(a);
    }).join(' ');
    const line = `${now().toISOString()} [${level}] ${text}\n`;
    try { stream?.write(line); } catch {}
    // 开发时还要能在终端看到
    if (process.env.NODE_ENV !== 'production') {
      (level === 'error' ? process.stderr : process.stdout).write(line);
    }
  }

  return {
    info: (...a) => write('info', a),
    warn: (...a) => write('warn', a),
    error: (...a) => write('error', a),
    dir: logDir
  };
};
```

### 接管现有 console

`main.js` 里装一次，**现有 6 处 `console.*` 不用改**：

```js
const logger = require('./logger')({ logDir: path.join(HERMES_DIR, 'logs') });
console.log = logger.info;
console.error = logger.error;
console.warn = logger.warn;
```

这样之前那些 `console.log('[hermes-pet] 自动导入密钥：', ...)`、`bridge listening on` 全都自动落盘。

### 渲染进程的日志也要能过来

`renderer/pet.js:31` 那个 `console.warn`（表情 key 找不到）现在只打在 DevTools 里，用户永远看不到。加一条通道：

`preload.js` 里加（**只加新通道，不动已有的**）：

```js
log: (level, ...args) => ipcRenderer.send('renderer-log', String(level || 'info'), args.map(String)),
```

`main.js` 里：

```js
ipcMain.on('renderer-log', (_e, level, args) => {
  (level === 'error' ? logger.error : level === 'warn' ? logger.warn : logger.info)('[renderer]', ...(Array.isArray(args) ? args : [args]));
});
```

`renderer/pet.js` 那个 `console.warn` 改成同时调 `window.pet.log('warn', ...)`。

### 菜单加一个入口

托盘右键菜单（`main.js:382` 附近）加一项：

## 四、第二步：三种崩溃都要接住

### 1. 主进程未捕获异常

在 `app.whenReady()` **之前**注册：

```js
// 主进程没接住的异常不能让进程静默消失——先记下来，再决定怎么退
process.on('uncaughtException', (error) => {
  logger.error('[main] uncaughtException', error);
  try {
    dialog.showErrorBox('赫尔墨兹遇到问题', `${error?.message || error}\n\n日志：${logger.dir}`);
  } catch {}
});

process.on('unhandledRejection', (reason) => {
  logger.error('[main] unhandledRejection', reason instanceof Error ? reason : String(reason));
});
```

`uncaughtException` **不要 `process.exit()`**。桌宠这种常驻小工具，一个非致命的异常把整个进程带走是最差的选择，记下来继续跑更合理。真到了进程状态没救的地步，用户会自己关掉重开。

`unhandledRejection` 尤其重要：现在 `pollHermes`、桥接的 async handler 里任何一个没 catch 的 await 都会静默变成 unhandled rejection，什么都不留下。

### 2. 渲染进程崩了

```js
win.webContents.on('render-process-gone', (_event, details) => {
  logger.error('[main] 渲染进程退出', { reason: details?.reason, exitCode: details?.exitCode });
  // 显卡驱动切换、内存不足这类问题是能自动恢复的，限次数重载
  if (++rendererCrashCount <= 3) {
    setTimeout(() => { if (win && !win.isDestroyed()) win.reload(); }, 800);
  } else {
    logger.error('[main] 渲染进程连续崩溃超过 3 次，停止自动重载');
  }
});
win.webContents.on('did-finish-load', () => { rendererCrashCount = 0; });
```

`rendererCrashCount` 用模块级变量。3 次上限是防止"崩了重载、重载又崩"的死循环烧 CPU。

`chatWin` 和 `menuWin` 也各挂一份，但**聊天窗崩了不做自动重载**（重载会把用户输入的东西丢掉），只记日志然后关闭窗口。

### 3. 桥接端口绑定失败

`bridge-server.js:117` 现在是：

```js
server.on('error', (error) => console.error('[hermes-pet] bridge error:', error.message));
```

只打印，不重试。`EADDRINUSE` 或系统暂时没端口时，桥接就彻底没了，但进程还活着、窗口还开着——用户看起来一切正常，实际插件一个都调不通。

改成重试：

```js
let bindAttempts = 0;
server.on('error', (error) => {
  logger.error('[hermes-pet] bridge error:', error.message);
  if (bindAttempts < 3) {
    bindAttempts += 1;
    setTimeout(() => { try { server.listen(0, '127.0.0.1', onListening); } catch {} }, 1000 * bindAttempts);
  } else {
    logger.error('[hermes-pet] 桥接服务连续失败 3 次，放弃（Hermes 插件将无法调用桌宠）');
  }
});
```

把 `listen` 的回调抽成 `onListening` 函数（现在是内联的），重试时复用。

## 五、第三步：状态文件坏了要留痕

`settings-store.js` 的 `readJson` 和 `pet-state.js` 的 `load()` 现在都是「读不出来就回落默认值」，静默的。

用户会遇到这个场景：某天开机，好感度从 82 变回 50，心情从 90 变回 72。他以为是 bug，你查日志发现什么都没有。

在 `readJson` 的 catch 里记一条：

```js
function readJson(file, fallback) {
  try {
    return JSON.parse(fs.readFileSync(file, 'utf8').replace(/^\uFEFF/, ''));
  } catch (error) {
    // 文件不存在是正常的（首次启动），文件坏了才是问题
    if (error?.code !== 'ENOENT') {
      logger?.warn(`[json-file] 读取失败，已回落默认值：${file}`, error.message);
    }
    return fallback;
  }
}
```

`logger` 需要从外部注入进 `settings-store`（工厂函数已经支持注入，加一个 deps 字段就行）。

5. **主进程异常**：用 `PET_DEV_SELFCHECK` 之类门控加一个 `setTimeout(() => { throw new Error('test') }, 3000)`，启动后 3 秒，日志里有 `[main] uncaughtException`，**进程还活着、桌宠还在**

## 七、不许做的

1. **`uncaughtException` 里不要 `app.quit()`**。桌宠是常驻小工具，非致命异常记下来继续跑，比直接消失好
2. **不改已有 IPC 通道名**。这轮只新增 `renderer-log`，其他一个不动
3. **日志不做同步写**。`createWriteStream` 就够，不要为了"保证写进去"改成 `appendFileSync`，那会在主线程上卡 I/O
4. **不加崩溃上报**。自用工具，本地日志够了，别引 Sentry 这类东西
5. **不动 `net.fetch`、不动 vendor/pixi.min.js、不动打包配置**（除了补那条 `*.bak.js` 排除）
